# PrivateMessage 消融规划

状态：早期局部规划，不单独作为跨仓库边界与施工真值。

本文关于独立 PrivateMessage 公共头、唯一 CP 签名、重加密式重试、严格分派和子协议职责
的分析仍然成立；其中 SSP/CP 身份绑定、版本和迁移顺序以
[`SSP + CP 协议族消融设计`](../SSP-CP协议族消融设计.md)及施工单为准。

本规划以新增 [`bsv8.ping.v1`](./05-Ping-Pong子协议.md) 为第三个私密子协议的设计压力测试，
判断现有抽象是否具有独立价值。消融目标不是追求最少文件或最少类型，而是删除不能提供
安全边界、互操作约束或明确开发体验的重复概念。

## 1. 评价维度

每个候选抽象按以下问题评估：

1. 删除后是否改变线上字节或签名输入；
2. 删除后是否更容易接受未验签、错误协议或错误关联的消息；
3. 是否在 Go 和 TypeScript 中表达同一约束；
4. 新增一个子协议需要修改多少处并行分支；
5. 调用方是否需要重复提供可以可靠推导的信息；
6. 是否把网络副作用、存储策略或业务语义错误地下沉到协议 SDK。

## 2. 协议方案消融

| 候选 | 删除或保留理由 | 决定 |
|---|---|---|
| 用 Deliver `content` 表示 Ping | 混合可靠投递、持久化 ACK 与短时探测 | 删除 |
| 把 ping/pong 加入 `MessageV1Body` | 有效期、去重重试和响应语义不同 | 删除 |
| 使用 ACK 作为 Pong | ACK 的可靠保存证明不能解释为短时响应 | 删除 |
| Ping body 增加 nonce | 外层随机 `message_id` 已提供唯一关联 | 删除 |
| 回显时间戳、序号、payload 或 status | 外层时间已存在，RTT 使用本地单调时钟，其余没有已确认需求 | 删除 |
| 分成 Ping 和 Pong 两个 protocol | 增加协议注册与分派，但没有隔离收益 | 删除 |
| 通用 Request/Response 或 Relation 抽象 | ACK、WebRTC 和 Pong 只有表面关联相似，语义和状态规则不同 | 删除 |
| 独立 `bsv8.ping.v1`，body 内区分 ping/pong | 保持语义隔离且只增加一个分派分支 | 保留 |
| Pong 引用 Ping 外层 `message_id` | 并发、乱序和重放情况下不可省略 | 保留 |

## 3. 必须保留的边界

以下分层具有独立的线上或安全职责，不能为了减少类型而合并：

```text
EncryptedEnvelopeV1
  └── PrivateMessage<Protocol, Body>
        └── 已注册子协议的严格 Body
```

- `EncryptedEnvelopeV1` 选择加密格式并绑定 channel、发送者、salt、nonce 和密文；
- `PrivateMessage` 提供统一编号、时间、签名输入和子协议分派；
- `protocol` 是同一稳定 inbox 内唯一可靠的 body 分派依据；
- 子协议严格 body 防止根据偶然同名字段猜测语义；
- 已验证运行时标记防止调用方把自行拼装的对象送入关系审查。

公开消息与私密消息也不能合并。二者的寻址、身份位置、签名作用域和机密性不同。

## 4. 建议删除或收敛的 SDK 抽象

### 4.1 收敛重复 Body 接口

当前 `PrivateBody` 与 `DecodedBody` 表达相同的协议名、JSON 表示和校验能力。目标设计只保留
一个内部 body 契约，编码和解码阶段使用具体状态类型保证调用顺序，不再复制接口。

验收门槛：删除后仍只能签名已注册 body，分派结果仍然是 Go/TypeScript 的封闭联合类型。

### 4.2 单一高层解码结果

当前 `Open` 先产生 raw `VerifiedPrivateMessage`，`Dispatch` 再复制相同公共字段并重新解析
body。目标高层入口一次完成解密、验签和注册协议分派，返回一个带已验证标记的强类型消息。

低层 raw 解密能力只有在存在明确的未知协议转发需求时才保留；V1 当前规定未知协议忽略，
因此不能仅为假设的扩展场景维持两套公共结果对象。

验收门槛：错误仍按 `OPEN_FAILED` 与 `UNSUPPORTED_PROTOCOL` 的既有安全边界归类，关系审查
不能接受调用方伪造对象，已验证 body 快照不能被修改。

### 4.3 关系校验接收完整已验证消息

Pong 关系校验应直接接收原 Ping 和 Pong 的已验证强类型消息，不新增 `PingContext`、
`PongContext`。后续可以评估让 ACK 关系校验也接收完整 Deliver/ACK，删除由调用方手工复制
发送者、接收者和编号的上下文对象。

验收门槛：校验器只能从已验证信封和 channel 提取身份，不能接受调用方覆盖身份字段。

### 4.4 私密去重和摘要冲突只保留一份

`(protocol, from_public_key, message_id)` 是 PrivateMessage 公共规则，不是应用 Deliver 专属
规则。目标设计由 inbox 层统一产生去重键并检查同键摘要冲突，子协议只决定重复消息的业务
行为。

Ping 的重复处理、Deliver 的重新 ACK 和 WebRTC 的重复信令策略仍由各自子协议规定，不能
被统一去重工具擅自决定。

### 4.5 集中固定协议元数据，不做动态注册

解析器和最大有效期应由同一处固定映射选择，避免在 body 类型检查、Dispatch 和时间校验中
分别维护平行 `switch/if`。该映射是 SDK 内部封闭表，不提供运行时插件注册、生命周期钩子
或通用处理器框架。

加入 Ping 后的最小元数据只有：

| protocol | body parser | 最大有效期 |
|---|---|---:|
| `bsv8.webrtc.signal.v1` | WebRTC signal | 2 分钟 |
| `bsv8.message.v1` | Deliver/ACK | 24 小时 |
| `bsv8.ping.v1` | Ping/Pong | 60 秒 |

线上 `protocol` 字段仍然保留，不能因为内部存在映射而从签名消息中删除。

## 5. 明确不进入协议 SDK 的能力

- 自动定时 Ping；
- 自动 Publish Pong；
- 在线/离线状态聚合；
- 速率限制器的具体算法和配额；
- 未完成探测的持久化；
- 网络重连和指数退避；
- 通用请求/响应、RPC 或健康检查 payload；
- 动态第三方子协议插件。

SDK 可以提供纯构造、严格解析和关系校验，但不能在解析函数中产生网络或存储副作用。

## 6. 分阶段执行计划

### 阶段 A：协议冻结

- 冻结 `bsv8.ping.v1` 字段、60 秒最大有效期和关系规则；
- 建立合法、非法、重复、乱序和超时共享向量；
- 明确旧实现对未知协议的忽略行为。

### 阶段 B：无行为重构

- 先用现有 fixture 锁定线上字节、摘要、签名、错误码和公开 API 行为；
- 收敛重复 body 接口、结果对象、去重帮助函数和协议元数据分支；
- Go、TypeScript 每完成一项都运行相同跨语言验收，禁止顺带修改线上格式。

### 阶段 C：加入 Ping/Pong

- 在收敛后的单一协议映射中注册 `bsv8.ping.v1`；
- 加入严格 body、最大有效期和完整消息关系校验；
- 验证旧协议 fixture 字节不变，新协议双向互操作一致。

### 阶段 D：API 收口

- 高层 API 只暴露已验证强类型消息；
- 评估低层 `Open`/`Dispatch` 是否仍有现实调用者，再决定保留、降级为高级接口或安排主版本
  迁移；
- 删除旧抽象必须遵循发布兼容策略，不能在 V1 补丁版本静默破坏调用方。

## 7. 完成判据

消融完成不能只以代码行减少判断，必须同时满足：

- 已有线上 JSON、JCS、digest、签名和固定密文向量完全不变；
- 已有 Hash、WebRTC、Deliver/ACK 行为和错误码不变；
- 新增私密子协议不再要求修改多套重复结果类型和去重实现；
- 未验证对象仍无法进入关系审查；
- Ping/Pong 没有引入自动网络副作用或通用请求响应框架；
- Go 与 TypeScript 对全部共享向量产生相同结果。
