# 私密收件箱 V1

频道名称：

```text
bsv8.inbox.<to_public_key_hex>
```

所有发给同一目标公钥的私密子协议消息都进入同一个稳定频道。V1 是使用双方长期密钥
ECDH 的基础加密产品，不使用一次性密钥。

## 1. 能力边界

私密收件箱提供：

- SSP 身份与报文发送者身份一致性检查；
- 双方长期 secp256k1 密钥 ECDH；
- HKDF-SHA256 和 AES-256-GCM 端到端加密；
- 每条业务消息一个 ECDSA 签名；
- 过期、重复消息检查和强类型子协议分派。

私密收件箱不提供离线队列、业务 ACK、前向安全或长期私钥泄露后的历史保护。

## 2. 加密信封

SSP `content_json` 只包含：

```jsonc
{
  "envelope_version": 1,             // V1 长期密钥 ECDH 加密信封
  "from_public_key": "02...",        // 发送者公钥，必须等于 SSP remote_public_key
  "kdf_salt": "base64url-32-byte",  // 每条消息重新生成
  "nonce": "base64url-12-byte",     // 每条消息重新生成
  "ciphertext": "base64url..."      // 密文 || 16 字节 GCM tag
}
```

所有字段必需。不支持 `envelope_version = 1` 的节点直接忽略，不能猜测加密格式。

发送者身份只由信封的 `from_public_key` 提供。接收者身份只由 channel 后缀提供。信封中
没有 `to_public_key`，也没有 `ephemeral_public_key`。

## 3. SSP 身份检查

发布入口在不解密消息的情况下检查：

```text
SSP remote_public_key == envelope.from_public_key
```

不相等时必须拒绝 Publish。SSP Core 不理解三方信封，因此该规则由三方频道 SDK 或接入
应用在调用 SSP 前执行。

## 4. 解密后的私密消息

```jsonc
{
  "protocol": "bsv8.message.v1",     // 子协议名称和版本
  "message_id": "base64url-32-byte", // 私密消息编号
  "issued_at_ms": 0,                  // 发布时间
  "expires_at_ms": 0,                 // 子协议消息过期时间
  "body": {},                         // protocol 对应的强类型正文
  "signature": "base64url-der"       // 整条私密消息唯一签名
}
```

密文中不重复 `from_public_key`、`to_public_key`，子协议 `body` 也不能包含身份字段或第二个
签名。

## 5. 强类型分派

```ts
interface PrivateMessage<TProtocol extends string, TBody> {
  protocol: TProtocol;      // 子协议名称和版本
  message_id: string;       // 私密消息编号
  issued_at_ms: number;     // 发布时间
  expires_at_ms: number;    // 过期时间
  body: TBody;              // 子协议独立正文
  signature: string;        // 整条私密消息唯一签名
}

type InboxPlaintext =
  | PrivateMessage<"bsv8.message.v1", MessageV1Body>
  | PrivateMessage<"bsv8.webrtc.signal.v1", WebRTCSignalV1Body>;
```

`signature` 只在 `PrivateMessage` 定义一次。Message 和 WebRTC 子协议只定义 `body`，不能
重新展开或重新签名公共消息头。

## 6. 长期密钥 ECDH

椭圆曲线私钥不直接加密 JSON。双方先使用长期密钥生成相同的 ECDH 共享秘密：

```text
发送方：ECDH(发送方长期私钥, 接收方长期公钥)
接收方：ECDH(接收方长期私钥, 发送方长期公钥)
```

接收方长期公钥来自 inbox channel 后缀，发送方长期公钥来自信封
`from_public_key`。共享秘密固定取 secp256k1 共享点 X 坐标的 32 字节大端编码。

同一对身份的 ECDH 共享秘密可以重复，但不能直接作为 AES 密钥。每条消息必须生成新的
32 字节 `kdf_salt`，再通过 HKDF-SHA256 派生消息密钥。

HKDF `info` 是以下对象的 JCS UTF-8：

```jsonc
{
  "scope": "bsv8.inbox.envelope.v1",
  "channel": "实际完整 inbox channel",
  "from_public_key": "信封发送者公钥"
}
```

方向被 `from_public_key` 和 channel 绑定，因此 A→B 与 B→A 使用不同的 HKDF 上下文。

## 7. 签名和加密流程

发送方：

1. 构造强类型私密消息，暂不填写 `signature`；
2. 按 V1 私密消息签名输入规则构造逻辑签名对象；
3. 使用发送方长期私钥生成唯一 ECDSA 签名并写入 `signature`；
4. 对包含签名的完整私密消息执行 JCS，得到加密明文；
5. 通过双方长期密钥 ECDH 得到共享秘密；
6. 生成新的 `kdf_salt`，使用 HKDF-SHA256 派生 32 字节 AES 密钥；
7. 生成新的 12 字节 `nonce`；
8. 构造 AES-GCM AAD；
9. 使用 AES-256-GCM 加密，tag 固定 16 字节；
10. 输出加密信封。

AAD 是以下对象的 JCS UTF-8：

```jsonc
{
  "channel": "实际完整 inbox channel",
  "envelope_version": 1,
  "from_public_key": "信封发送者公钥",
  "kdf_salt": "base64url-32-byte",
  "nonce": "base64url-12-byte"
}
```

该 AAD 对象不作为额外字段传输；接收方使用实际 channel 和信封字段重新构造。

## 8. 接收流程

1. 确认 channel 等于 `bsv8.inbox.<自己的公钥>`；
2. 严格解析信封并检查 `envelope_version`；
3. 验证 `from_public_key` 是有效 secp256k1 公钥；
4. 使用自己的长期私钥和 `from_public_key` 执行 ECDH；
5. 重建 HKDF `info` 和 AAD，派生 AES 密钥并解密；
6. 严格解析私密消息并拒绝重复字段；
7. 检查 `issued_at_ms < expires_at_ms`、消息未过期，且发布时间最多比本地晚 60 秒；
8. 使用信封 `from_public_key` 验证私密消息唯一签名；
9. 根据 `protocol` 使用对应子协议结构解析 `body`；
10. 按 `(protocol, from_public_key, message_id)` 标记消息是否重复；
11. 把消息和重复标记交给对应子协议处理器。

任意一步失败都直接忽略，不返回解密或验签细节。

## 9. 隐私和安全边界

观察 SSP channel 的节点可以看到：

- 发送者 `from_public_key`；
- 接收者 channel 公钥；
- 信封版本、salt、nonce、密文长度和 Publish 时间。

观察者不能读取 `protocol`、消息编号、正文、签名、SDP 或 ACK 关联。V1 不具备前向安全：
任意一方长期私钥未来泄露后，配合另一方公开公钥可以解密历史录制密文。

这是 V1 基础安全级别的明确取舍。更高安全级别通过其他产品或新信封版本提供。

## 10. 分派流程

```text
收到 bsv8.inbox.<自己的公钥>
→ 使用长期私钥 ECDH 解密
→ 验证唯一签名
→ 读取 protocol
   ├── bsv8.webrtc.signal.v1 → WebRTCSignalV1Body 处理器
   ├── bsv8.message.v1       → MessageV1Body 处理器
   └── 未知协议              → 忽略
```
