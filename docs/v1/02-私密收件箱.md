# 私密收件箱 V1

频道：

```text
bsv8.inbox.<recipient_public_key_hex>
```

接收者公钥只由 channel 后缀确定。

## 1. 加密信封

完整 SSP `content_json`：

```json
{
  "envelope_version": 1,
  "from_public_key": "02...",
  "kdf_salt": "base64url-32-byte",
  "nonce": "base64url-12-byte",
  "ciphertext": "base64url-ciphertext-and-16-byte-tag"
}
```

`from_public_key` 是 CP 发送者公钥，只出现一次。它用于 ECDH、KDF/AAD 和解密后的签名
验证。它不表示 SSP 付款人，也不要求等于 libp2p 连接公钥。

## 2. 私密消息

解密明文：

```json
{
  "protocol": "bsv8.message.v1",
  "message_id": "base64url-32-byte",
  "issued_at_ms": 0,
  "expires_at_ms": 0,
  "body": {},
  "signature": "base64url-der"
}
```

PrivateMessage 不重复 `from_public_key`；验签公钥取信封。各子协议 body 不得再次携带
公钥、message_id、时间或签名。

## 3. 加密

```text
sender:    ECDH(sender_private_key, recipient_public_key)
recipient: ECDH(recipient_private_key, envelope.from_public_key)
```

- 共享点 X 坐标进入 HKDF-SHA256；
- 每次加密生成新的 32 字节 salt 和 12 字节 nonce；
- HKDF info 绑定 scope、实际 inbox channel 和 `from_public_key`；
- AES-GCM AAD 再绑定 envelope_version、salt 和 nonce；
- ciphertext 包含 16 字节 GCM tag。

## 4. 签名与构造顺序

1. 构造 protocol、message_id、时间和强类型 body；
2. 使用 `bsv8.private-message.v1` domain、实际 channel 和发送者公钥构造签名输入；
3. 生成唯一 strict DER、low-S ECDSA 签名；
4. 把完整 PrivateMessage 规范化后加密；
5. 输出只含一个发送者公钥的信封。

签名不包含 SSP request_id、libp2p 公钥或付款账户。

## 5. 接收

1. 严格解析 channel 和信封；
2. 使用自己的私钥与信封发送者公钥 ECDH；
3. 重建 HKDF/AAD 并解密；
4. 严格解析 PrivateMessage；
5. 检查时间；
6. 使用信封 `from_public_key` 验证唯一签名；
7. 按 protocol 严格分派 body；
8. 按 `(protocol, from_public_key, message_id)` 去重。

Supplier 没有接收者私钥，因此只能执行第 1 步以及大小/策略检查，不能声称已经验证内层
签名。

## 6. 重试

同一条已签名 PrivateMessage 重试时：

- 保持 message_id、时间、body 和 signature；
- 可以重新加密并生成新的 salt/nonce；
- 接收方仍按 CP 作者 + message_id 去重；
- 每次 Supplier 转发都必须保持该次收到的 `content_json` 字节不变。

是否重新收费由 SSP request_id 和 Supplier 策略决定，不由 CP message_id 决定。

## 7. 子协议

```text
bsv8.webrtc.signal.v1 → WebRTC
bsv8.message.v1       → Deliver/ACK
bsv8.ping.v1          → Ping/Pong
```

V1 使用长期密钥 ECDH，不提供前向安全。
