# 三方频道协议族消融实验

状态：早期局部实验记录，不再作为字段与版本施工真值。

本文对 SDK 表面、CP 独立公共消息头和各子协议职责的盘点仍可作为设计证据；其中
“SSP 身份必须等于 CP 作者”、已发布状态、V2 Publication 及迁移顺序等结论已被后续的
libp2p + SSP / CP 整体设计取代。实际施工只以
[`SSP + CP 协议族消融设计`](../SSP-CP协议族消融设计.md)和对应施工单为准。

两个项目尚未正式发布，因此协议版本号保持原值、项目包版本调整为 0.2.0；不得独立执行
本文的 SSP 边界或版本迁移章节。

本文中的“删除”分为三个等级：

| 等级 | 含义 |
|---|---|
| SDK 删除 | 不改变线上 JSON、签名输入或密文，可在下一次破坏性 SDK 发布中实施 |
| V2 删除 | 改变线上字段或关联规则，必须使用新的 channel、protocol 或 envelope version |
| 拒绝删除 | 删除会损害安全、互操作、关联唯一性或明确语义 |

## 1. 实验目标

消融不以文件数或代码行最少为目标，而以最少的独立概念完成以下不变量：

1. 公开 Hash 请求可认证、可过期、可去重并可被后续连接引用；
2. 私密消息绑定发送者、接收者、方向、子协议、时间和唯一签名；
3. 同一 inbox 内的 body 不能靠字段猜测协议；
4. Deliver/ACK、WebRTC 和 Ping/Pong 的可靠性语义不混用；
5. 未验签或由调用方伪造的对象不能进入关系校验；
6. Go 与 TypeScript 对同一线上输入产生相同结果；
7. 协议 SDK 不承担 Publish、自动响应、定时任务或永久状态存储。

若删除一个抽象不能减少调用方概念、维护分支或线上字节，或者会把约束转移成隐含约定，
则该消融失败。

## 2. 目标最小分层

```text
SSP Publish
├── bsv8.hash.request.v1
│     └── 已验证 HashRequest
└── bsv8.inbox.<目标公钥>
      └── EncryptedEnvelopeV1
            └── 已验证并已分派的 PrivateMessage
                  ├── WebRTCSignal
                  ├── Deliver / ACK
                  └── Ping / Pong
```

保留三层且只保留三层：

- SSP channel 决定公开广播或目标 inbox；
- `EncryptedEnvelopeV1` 决定密码格式和 ECDH 参与方；
- `PrivateMessage.protocol` 决定严格 body 结构和语义。

不能再增加通用 Command、Request/Response、Relation、Handler、Capability 或 Lifecycle 层。

## 3. 频道和公共壳消融

| 候选删除项 | 对照结果 | 判决 |
|---|---|---|
| 合并公开 Hash channel 与私密 inbox | 公开发现和定向密文具有不同寻址、身份位置与可见性 | 拒绝删除 |
| 为每个私密子协议建立独立 inbox channel | 可以删除 `protocol`，但会增加订阅、寻址和版本迁移负担 | 拒绝 |
| 删除私密消息 `protocol`，根据 body 猜测 | 同名字段可跨应用出现，无法稳定分派 | 拒绝 |
| 合并公开与私密签名 scope | 允许跨上下文复用签名 | 拒绝 |
| 为未来公开协议设计通用公开消息 SDK 类型 | 当前只有 Hash 请求，不产生现实复用 | 不新增；现有 V1 `body` 只作为线上结构保留 |
| 接收端根入口自动判断所有 channel | 需要可选私钥，并产生同步/异步联合返回类型 | SDK 删除 |

SSP 服务端的 Publish 准入仍需要按 channel 路由，但它只返回成功/错误，不解密 inbox，
不返回公开/私密联合消息。这个准入路由与被删除的接收端根 decoder 是两种职责。

公开和私密消息的线上壳保持不变，但 SDK 不再为“未来可能出现的频道”预先建立通用框架。

## 4. Hash 请求消融

### 4.1 线上字段

| 字段或结构 | 删除后的损失 | 判决 |
|---|---|---|
| `from_public_key` | 公开消息不再能脱离 SSP 连接上下文自验证，签名验证也缺少明确密钥 | 保留 |
| `message_id` | 无法稳定去重，也无法让 WebRTC offer 引用一次具体请求 | 保留 |
| `issued_at_ms` | 无法检查未来消息和表达签名发生时间 | 保留 |
| `expires_at_ms` | 旧广播可以被长期重放，提供者不知道请求是否仍有效 | 保留 |
| `signature` | 真实性完全依赖 SSP 转发路径，消息不能独立验真 | 保留 |
| `body.hash` | 失去请求资源的唯一真值 | 保留 |
| `body.locators` | 提供者不知道如何连接请求者 | 保留 |
| locator `kind` | 无法严格区分带 address 的 multiaddr 与能力标记 | 保留 |
| `webrtc-sdp` locator | 提供者无法知道请求者是否愿意接收 WebRTC offer | 保留 |
| locator 数组顺序 | 失去请求者的连接方式偏好 | 保留 |

Hash body 已经正确消除了 `hash_algorithm`、`hash_encoding`、MIME、filename 和业务 kind；
不能重新加入这些字段。

公开 Hash 请求现在与私密消息统一采用 60 秒未来时钟容差：验证时拒绝
`issued_at_ms > now_ms + 60_000`，错误为 `INVALID_TIME`。Go、TypeScript 共享向量覆盖
恰好 `now_ms + 60_000` 的接受边界、`now_ms + 60_001` 的拒绝边界，以及远期但自身有效期
不超过 10 分钟的请求；这只收紧接受集合，不改变字段、签名格式或协议版本。

### 4.2 SDK 抽象

- 删除 `HashRequestMessage = SignedMessage` 语义别名，只保留一个已签名类型；
- 删除 Hash 模块重复的 `NewMessageID`，统一使用公共原语；
- 删除 `SameContent`，保留统一的去重键和摘要冲突路径；
- `ReviewAdmission` 只做身份相等检查，不再返回无人消费的
  `AdmissionReviewedMessage/AdmissionReviewedHashRequest` 品牌包装；
- 方法形式和函数形式的 `ReviewAdmission` 只保留一种；
- 保留 `VerifiedHashRequest` 的不可伪造标记和不可变快照。

身份准入规则本身不能删除。删除的是“检查成功后再包装一个新对象”的表示层。

## 5. 私密信封消融

### 5.1 加密信封字段

| 字段 | 删除实验 | 判决 |
|---|---|---|
| `envelope_version` | 接收方只能猜测 KDF、AAD 和密文格式 | 保留 |
| `from_public_key` | 接收方无法选择 ECDH 对端或验证发送身份 | 保留 |
| `kdf_salt` | 长期 ECDH 共享秘密会重复使用同一消息密钥 | 保留 |
| `nonce` | AES-GCM 缺少显式 nonce；改为派生 nonce 需要新的密码格式审查 | V1 保留 |
| `ciphertext` 与 GCM tag | 失去机密性或密文完整性 | 保留 |

可以设想从 `kdf_salt` 派生 nonce 的新 envelope version，但它是密码设计变更，不是普通字段
清理。在没有独立密码学审查、误用分析和双语固定向量前，本实验不批准该删除。

### 5.2 双重认证

AES-GCM tag 不能替代私密消息 ECDSA 签名。双方都知道 ECDH 共享秘密，接收者可以生成有效
GCM 密文；只有发送者签名能够证明逻辑消息来自声明的长期身份。

早期曾要求 `SSP remote_public_key == envelope.from_public_key`；整体边界对齐后删除这项
要求。前者是 libp2p/SSP 调用者和付款人，后者是 CP 作者与 ECDH 对端，A 可以代发 B 的
合法信封。Supplier 仍应在扣费前检查可见信封结构、公钥曲线形状和资源上限，但不能把
两层公钥不相等当作错误，也不需要 `AdmissionReviewedEnvelope` 品牌包装。

## 6. PrivateMessage 消融

### 6.1 线上字段

| 字段 | 独立职责 | 判决 |
|---|---|---|
| `protocol` | 同一 inbox 内严格选择子协议和版本 | 保留 |
| `message_id` | 去重、重试和跨消息关联 | 保留 |
| `issued_at_ms` | 未来时钟检查和签名时间上下文 | 保留 |
| `expires_at_ms` | 限制重放窗口并表达子协议生命周期 | 保留 |
| `body` | 隔离子协议字段，允许 Deliver content 为任意 JSON 值 | 保留 |
| `signature` | 提供方向明确、非对称的逻辑消息认证 | 保留 |

身份公钥和 channel 不进入密文内层是正确消融：发送者取信封，接收者取 channel 后缀，不能
重新添加重复身份字段。

### 6.2 解码结果

当前低层 `Open → VerifiedPrivateMessage` 和高层
`Dispatch → DecodedInboxMessage` 保存两份相同元数据，并在 Dispatch 中再次解析 body。
目标设计为单一默认入口：

```text
openInbox
→ 解密
→ 时间与签名验证
→ 固定协议分派
→ VerifiedInboxMessage<ConcreteBody>
```

只保留一个不可伪造标记、一个不可变 body 快照和一套公共字段访问器。未知协议按
`UNSUPPORTED_PROTOCOL` 终止，不为假设的透明转发保留 raw 公共结果类型。

其余 PrivateMessage 消融结论见
[PrivateMessage 消融规划](./PrivateMessage-消融规划.md)。

## 7. WebRTC 消融

### 7.1 V1 中不能直接删除

`request_message_id` 把 offer 绑定到公开 Hash 请求；SDP、ICE candidate 和
`end-of-candidates` 分别承担 WebRTC 标准信令职责，均应保留。

V1 的独立 `session_id` 和嵌套 `signal` 可以工作，但不是最小设计：

- offer 外层已经拥有随机、签名绑定的 `message_id`；
- `session_id` 只是第二个同长度随机编号；
- answer/ICE 同时重复 `request_message_id` 和 `session_id`；
- `signal` 只有一个使用者，额外嵌套不提供命名隔离。

因为这些字段已经属于 `bsv8.webrtc.signal.v1` 签名内容，不能在 V1 中删除。

### 7.2 协调后的 V2 候选

只有在协议族进入协调后的 V2 时，采用以下最小结构：

Offer 的外层 `message_id = O` 同时成为会话编号：

```jsonc
{
  "type": "offer",
  "request_message_id": "H",
  "sdp": "v=0..."
}
```

Answer 和 ICE 只引用原 Offer：

```jsonc
{ "type": "answer", "offer_message_id": "O", "sdp": "v=0..." }

{
  "type": "ice-candidate",
  "offer_message_id": "O",
  "candidate": {
    "candidate": "candidate:...",
    "sdp_mid": "0",
    "sdp_m_line_index": 0
  }
}

{ "type": "end-of-candidates", "offer_message_id": "O" }
```

本地会话键从：

```text
(request_message_id, offerer_public_key, session_id)
```

缩减为：

```text
(offerer_public_key, offer_message_id)
```

Hash 请求关系只在验证 Offer 时检查一次，后续信令通过已保存 Offer 上下文得到 Hash 请求。
这会删除：

- 线上 `session_id`；
- 公共 `SessionID` 原语及生成/解析 API；
- `SessionKey` 三元组；
- 所有信令的 `signal` 嵌套；
- answer/ICE 重复携带的 `request_message_id`。

该候选需要同时解决 Hash locator 对 WebRTC 信令版本的协商。没有明确协商时，继续保留并
实现 V1，不能向只声明 `webrtc-sdp` 的旧节点盲发 V2。

## 8. 应用消息消融

| 候选删除项 | 结果 | 判决 |
|---|---|---|
| 把 Deliver content 直接放到 PrivateMessage body | 任意 JSON content 无法与 ACK 形成严格联合 | 拒绝 |
| 删除 `type` | 只能靠字段存在性猜 Deliver/ACK | 拒绝 |
| 删除 ACK 自身 `message_id` | ACK 不再是可签名、去重的独立消息 | 拒绝 |
| 删除 `acknowledged_message_id` | 并发 Deliver 无法关联 | 拒绝 |
| 用 SSP Publish 成功替代 ACK | 只能证明进入广播入口，不能证明接收端可靠保存 | 拒绝 |
| 自动 ACK | SDK 会在应用尚未持久化时产生错误可靠性承诺 | 拒绝 |
| 通用 Request/Response 抽象 | 混淆可靠保存、业务结果和短时响应 | 拒绝 |

Deliver/ACK 的线上结构已经接近最小。SDK 只删除应用模块重复定义的私密去重键和摘要冲突
函数，统一使用 inbox 层结果；ACK 关系校验改为接收两条完整已验证消息，不再让调用方手工
拼装 `DeliveryContext/AckContext`。

## 9. Ping/Pong 消融

[`bsv8.ping.v1`](./05-Ping-Pong子协议.md) 已经使用消融后的最小正文：

```text
Ping = { type: "ping" }
Pong = { type: "pong", ping_message_id }
```

外层 `message_id` 已替代 nonce、sequence 和发送时间；本地单调时钟替代线上 RTT 时间戳；
Pong 关系替代通用响应抽象。不能再添加 payload、status、ACK 或自动 Publish。

## 10. SDK 公共表面消融

### 10.1 删除项

| 当前抽象 | 实验依据 | 目标 |
|---|---|---|
| 根级 `DecodeChannel/decodeChannel` | Go 需要 tagged union 和可选私钥；TS 甚至返回值或 Promise 的联合 | 删除，调用明确的 public/inbox 入口 |
| 根级 public/inbox 薄包装 | 只转发到子模块，没有增加约束 | 删除 |
| 运行时 `ProtocolRegistry/PROTOCOL_REGISTRY` | 代码不使用，只复制 `protocols.json` 和常量 | 删除，保留内部固定分派表 |
| TypeScript Go 风格大写别名 | 当前共有 37 个别名，扩大声明、文档和兼容表面 | 全部删除，只保留 camelCase |
| Go 语义 type alias | `HashRequestMessage`、`PrivateMessage` 没有新增类型安全 | 删除 |
| 重复 convenience wrapper | Hash `NewMessageID`、双形式 Review、根级 Review 等 | 每项只保留一个归属明确的入口 |
| AdmissionReviewed 品牌结果 | 没有后续 API 消费，只复制原对象 | 删除结果类型，保留无状态身份检查 |
| `PrivateBody` 与 `DecodedBody` | 方法集合相同 | 合并为一个内部契约 |
| Go body 的 `ProtocolName()` | 调用路径从不读取；`Protocol` 和固定类型映射已经校验配对 | 删除方法，线上 `protocol` 保留 |
| Go `MessageV1Body.MessageType()` | 调用路径从不读取，具体 Deliver/Ack 类型已经是分支 | 删除方法，线上 `body.type` 保留 |
| `VerifiedPrivateMessage` 与 `DecodedInboxMessage` | 22 个重复访问器并重复保存元数据 | 合并为一个已验证强类型结果 |
| appmessage 私密去重类型 | 与 inbox 去重键和冲突检查完全重复 | 删除，私密去重只在 inbox |
| 手工 ACK/Pong Context | 调用方可以复制错身份或编号 | 改为完整已验证消息参数 |
| `SameContent` 加冲突检查双 API | 同一摘要关系表达两次 | 只保留一种冲突判定 |
| TypeScript symbol + WeakSet + frozen 三重品牌 | WeakSet 已能证明 SDK 创建，冻结已在构造时保证 | 保留 WeakSet 与冻结，删除可复制 symbol 和重复检查 |
| 只为 fixture 暴露的 raw helper | 扩大生产 API，且没有完整用户工作流 | 移入内部或明确测试入口 |

TypeScript 不需要模仿 Go 的命名；跨语言一致性只要求语义、线上字节、错误码和能力一致。

待签名消息仍显式携带 `Protocol` 与具体 Body。TypeScript 用 discriminated union、Go 用固定
类型映射检查二者匹配；不再让每个 Go body 额外实现一个从未使用的 `ProtocolName()` 来表达
第三遍相同事实。

### 10.2 保留项

- 按协议拆分的模块或 package；
- 强类型公钥、私钥、MessageID、Hash 和 Signature；
- 已验证结果的不可伪造标记与防御性快照；
- `Sign` 与 `SealSigned` 分离，因为可靠重试必须重加密同一已签名 Deliver；
- `SignAndSeal` 作为绝大多数首次发送的组合入口；
- `ParseEnvelope`，因为 SSP 适配层需要在没有接收方私钥时执行准入检查；
- 结构化稳定错误码；
- 严格 JSON、JCS、字节、深度和节点资源限制；
- 每个具体联合分支的构造器和严格 parser。

### 10.3 错误 API

错误分类本身保留；`UNKNOWN_FIELD`、`OPEN_FAILED`、`MESSAGE_ID_CONFLICT` 和
`INVALID_RELATION` 表达不同处理策略，合并不会减少校验逻辑。

Go 当前同时提供 `...Code` 常量、`Err...` sentinel 和 `IsErrorCode`。目标只保留：

- `ChannelProtocolError.Code` 供日志和跨语言记录；
- `Err...` 供 `errors.Is` 使用。

删除 `...Code` 镜像常量和 `IsErrorCode` 便利层。TypeScript 保留单一 `ERROR_CODES` 与
`ChannelProtocolError.code`。

## 11. 固定协议映射

删除公共运行时 registry 不等于散落 `switch`。SDK 内部只保留一个封闭映射：

| protocol | parser | 最大有效期 |
|---|---|---:|
| `bsv8.webrtc.signal.v1` | WebRTCSignalV1 | 2 分钟 |
| `bsv8.message.v1` | Deliver/ACK | 24 小时 |
| `bsv8.ping.v1` | Ping/Pong | 60 秒 |

该映射同时服务签名前 body/protocol 配对、解密后分派和最大有效期检查。它不能变成运行时
插件系统；新增线上协议仍然要求新文档、常量、parser 和共享向量。

## 12. 实施顺序

### 阶段 A：锁定 V1

- 将现有 JSON、JCS、digest、签名、密文、错误码和关系 fixture 作为不可变基线；
- 为公开与私密准入、未知协议和全部公共入口补充使用清单；
- 不修改 `bsv8.hash.request.v1`、`bsv8.inbox` envelope v1、WebRTC v1 或 Message v1 字节。

### 阶段 B：SDK 无行为消融

按以下顺序删除，每一步都运行 Go、TypeScript 和跨语言验收：

1. TypeScript 大写别名、Go 语义别名和重复薄包装；
2. 公共 runtime registry 与根级自动 channel decoder；
3. AdmissionReviewed 包装和重复去重帮助函数；
4. 单一 PrivateMessage body 契约与单一解码结果；
5. 关系校验改用完整已验证消息；
6. 收敛错误访问方式和测试专用 helper。

这些是公开 API 破坏性变化，必须集中在一次明确的 SDK 迁移发布中，不能跨多个补丁版本
逐步制造半新半旧表面。

### 阶段 C：加入 Ping/Pong

在精简后的固定协议映射加入 `bsv8.ping.v1`，不复制新的 raw/decoded 类型、去重类型、
Context 或命名别名。

### 阶段 D：取消协议 V2 实验

项目尚未正式发布，本轮只调整项目包版本，所有协议版本号保持原值。因此不启动 WebRTC
新协议版本、Hash locator 版本协商或双版本兼容；`session_id` 与 `signal` 结构继续保留。

## 13. 完成判据

协议族消融完成必须同时满足：

- V1 全部固定线上向量逐字节不变；
- 不再存在根级自动 channel union decoder；
- 不再存在公开 runtime registry 或 TypeScript Go 风格别名；
- 私密消息只有一个已验证强类型结果和一套去重规则；
- 准入检查不再创建无人消费的品牌包装；
- ACK、WebRTC、Pong 关系都从已验证消息提取身份，调用方不能覆盖；
- Ping/Pong 没有引入自动网络副作用；
- 不修改 WebRTC、Hash、Inbox 或 SSP 的任何协议版本号；
- Go、TypeScript 与跨语言 fixture 全部通过。

## 14. 最终判决摘要

线上 V1 的大部分复杂度来自真实安全和关联需求，不应为了视觉简洁删除。主要冗余位于 SDK
表示层，可以在不改变任何线上字节的情况下大幅收敛。

不批准协议 V2 原型进入本轮施工。`session_id`、`signal` 嵌套、独立 salt/nonce、签名、
时间、message ID、protocol、ACK 引用和 locator 均保留。
